# Feature Specification: Внедрение Spec-Driven Development в IPSAS

**Feature Branch**: `001-speckit-baseline`

**Created**: 2026-09-28

**Status**: Draft

**Input**: User description: "Внедрить фреймворк SDD SpecKit в репозиторий IPSAS, развернуть
локально, изучить проект и зафиксировать baseline: конституцию, стек, домен, security-инварианты,
quality gate."

## Overview

IPSAS — зрелый Flask-сервис без БД: 12 сервисов UI, 155 модулей, 263 теста, документированные
слои и compatibility shim'ы. Правила проекта зафиксированы в прозе (`README.md`,
`STRUCTURE.md`, `DEPLOYMENT.md`), но не проверяются автоматически, а quality gate нестабилен:
в `pyproject.toml` нет `[tool.ruff]`, поэтому набор правил линтера зависит от установленной
версии (53 замечания при `E4,E7,E9,F` против 1300 при default-наборах `ruff 0.16.9`).

Эта фича вводит Spec-Driven Development как способ работы: репозиторий получает инфраструктуру
Spec Kit (`.specify/`, slash-команды), конституцию с принципами, выведенными из кода, и baseline
спецификации/плана/задач, с которого начинается каждая следующая фича. Код приложения этой фичей
не меняется.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Локальный запуск по инструкции (Priority: P1)

Новый разработчик на чистой машине выполняет шаги локального запуска и получает рабочее
приложение, не задавая вопросов и не читая исходный код.

**Why this priority**: без поднятого приложения остальные сценарии не проверяемы. Это самый
короткий путь к проверке любой фичи.

**Independent Test**: на чистом клоне выполнить шаги развёртывания и получить HTTP 200 на
`/health`, `/health/ready`, `/dashboard` и на всех 12 маршрутах `/services/*`.

**Acceptance Scenarios**:

1. **Given** чистый клон и Python 3.10+, **When** создаётся venv, ставятся зависимости из
   `requirements-dev.txt`, копируется `.env.example` в `.env`, запускается `python run.py`,
   **Then** сервер поднимается на порту из `PORT` (по умолчанию 5000) и отвечает 200.
2. **Given** поднятый сервер, **When** выполняется `GET /health`, **Then** тело ответа —
   `{"status":"ok","service":"ipsas"}`.
3. **Given** поднятый сервер, **When** выполняется `GET /health/ready`, **Then** ответ 200,
   а проверка фиксирует доступность записи в temp и наличие `journal3.xsd`.
4. **Given** поднятый сервер, **When** выполняется `pytest`, **Then** 263 теста проходят без
   ошибок и пропусков.

---

### User Story 2 - Описание новой фичи через Spec Kit (Priority: P1)

Разработчик формулирует намерение на естественном языке, и агент создаёт каталог фичи со
спецификацией, планом и задачами, связанными с существующей архитектурой.

**Why this priority**: это основная ценность внедрения — превратить намерение в проверяемый
план до написания кода.

**Independent Test**: запустить `/speckit.specify` с описанием вымышленной фичи и убедиться,
что создан `specs/<NNN>-<slug>/spec.md` без незаполненных плейсхолдеров.

**Acceptance Scenarios**:

1. **Given** репозиторий с `.specify/`, **When** выполняется `/speckit.specify` с описанием,
   **Then** создаётся каталог `specs/<NNN>-<slug>/` с заполненным `spec.md`, приоритетными
   user stories и измеримыми критериями успеха.
2. **Given** созданная спецификация, **When** выполняется `/speckit.plan`, **Then** появляется
   `plan.md` с техническим контекстом, ссылающимся на реальные модули `ipsas/`.
3. **Given** план, **When** выполняется `/speckit.tasks`, **Then** появляется `tasks.md` —
   упорядоченный список задач, каждая из которых трассируется к элементу плана.
4. **Given** описанная фича, **When** выполняется `/speckit.implement`, **Then** задачи
   отмечаются выполненными по мере подтверждения, а не «по умолчанию».

---

### User Story 3 - Проверка артефактов на соответствие конституции (Priority: P1)

Автор плана и ревьюер получают машинно-проверяемый список требований, нарушение которых
блокирует реализацию.

**Why this priority**: конституция без проверки в артефактах вырождается в декларацию.

**Independent Test**: создать план, нарушающий принцип слоистости (логика в маршруте), и
убедиться, что gate это отмечает.

**Acceptance Scenarios**:

1. **Given** заполненная конституция, **When** выполняется `/speckit.plan`, **Then** gate
   конституции проверяется и отсутствие нарушений подтверждается до создания `plan.md`.
2. **Given** артефакты фичи, **When** выполняется `/speckit.analyze`, **Then** выдаётся отчёт о
   согласованности spec/plan/tasks и о нерешённых `[NEEDS CLARIFICATION]`.
3. **Given** нарушение принципа, **When** выполняется `/speckit.analyze`, **Then** нарушение
   указано явно, с цитатой принципа и указанием на затронутый артефакт.

---

### User Story 4 - Ревьюер видит правила проекта в машиночитаемом виде (Priority: P2)

Новый участник команды получает перечень правил проекта из одного файла, а не из четырёх
документов прозы.

**Why this priority**: снижает время онбординга, но не блокирует саму SDD-практику.

**Independent Test**: открыть `.specify/memory/constitution.md` и найти в нём ссылки на
конкретные модули и инварианты, а не абстрактные лозунги.

**Acceptance Scenarios**:

1. **Given** репозиторий, **When** открыт `.specify/memory/constitution.md`, **Then** в нём
   зафиксированы: слоистость, shim-паттерн, dry-run для записей, SSRF/XML/ZIP/CSRF-инварианты,
   quality gate, требование одного worker, стек и Definition of Done.
2. **Given** конституция, **When** в неё добавляется принцип, **Then** версия повышается по
   SemVer и в файле указан `Last Amended`.

---

### User Story 5 - Стабильный quality gate (Priority: P2)

Ревьюер и CI получают одинаковый результат линтера независимо от того, какая минорная версия
`ruff` установлена.

**Why this priority**: сейчас `ruff check ipsas tests` из `README.md` падает или проходит в
зависимости от окружения, что делает критерий приёмки неисполнимым.

**Independent Test**: установить две разные версии `ruff` в диапазоне `>=0.6.0,<1` и получить
идентичный список замечаний.

**Acceptance Scenarios**:

1. **Given** репозиторий, **When** выполняется `ruff check ipsas tests`, **Then** набор
   замечаний определяется конфигурацией в `pyproject.toml`, а не версией ruff.
2. **Given** зафиксированный baseline, **When** выполняется линт, **Then** вывод сопоставим с
   числом, записанным в конституции, и расхождение видно явно.

---

### User Story 6 - Спецификации живут в репозитории и доступны команде (Priority: P3)

Спецификации коммитятся в тот же репозиторий и тот же GitLab, что и код.

**Why this priority**: полезно, но не блокирует индивидуальную работу по SDD.

**Independent Test**: `git ls-files specs` показывает закоммиченные артефакты; `.gitignore`
не исключает `specs/`.

**Acceptance Scenarios**:

1. **Given** каталог `specs/`, **When** выполняется `git add specs/`, **Then** файлы не
   игнорируются, включая `.specify/` и `.opencode/commands/`.
2. **Given** закоммиченная спецификация, **When** участник команды клонирует репозиторий,
   **Then** он может продолжить работу с фичей без дополнительной установки, кроме
   `specify init` как зависимости.

---

### Edge Cases

- Установленная `ruff` версия несовместима с синтаксисом `pyproject.toml`
  (`[tool.ruff]`): команда падает с ошибкой парсинга — конфигурация должна оставаться в
  синтаксисе, поддерживаемом всем допустимым диапазоном `>=0.6.0,<1`.
- Путь пользователя содержит кириллицу: MSYS-bundled `ssh.exe` из Git для Windows не может
  прочитать `~/.ssh/known_hosts` и `git clone` падает с `Host key verification failed`.
  Обход — `core.sshCommand` на системный `C:\Windows\System32\OpenSSH\ssh.exe`.
- Политика выполнения PowerShell запрещает запуск `.specify/scripts/powershell/*.ps1`:
  нужен `Set-ExecutionPolicy -Scope Process Bypass` или запуск с `-ExecutionPolicy Bypass`.
- Отсутствует Python 3.11 (только 3.12): сборка проходит, но `runtime.txt` продолжает
  указывать 3.11 — расхождение окружения и production фиксируется, а не «лечится» сменой
  `runtime.txt` в рамках внедрения SDD.
- `IPSAS_ENV=production` без `SECRET_KEY`, с `FLASK_DEBUG=true` или пустым
  `ISSUE_FETCH_ALLOWED_HOSTS`: приложение обязано падать на старте, а не стартовать.
- Каталог уже содержит файлы (репозиторий не пуст): `specify init` требует `--force`, иначе
  интерактивное подтверждение недоступно для агента.
- Таймауты и лимиты в dev-режиме: `MAX_CONCURRENT_JOBS`, `MAX_JOB_QUEUE`,
  `RATE_LIMIT_PER_MINUTE` держатся в памяти процесса, поэтому проверка параллельных сценариев
  на нескольких процессах даёт ложные результаты.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: В репозитории MUST присутствовать инфраструктура Spec Kit: `.specify/` с
  шаблонами (`spec`, `plan`, `tasks`, `checklist`, `constitution`), скриптами для PowerShell и
  `memory/constitution.md`.
- **FR-002**: В репозитории MUST присутствовать команды агента для opencode в
  `.opencode/commands/`: `speckit.constitution`, `speckit.specify`, `speckit.clarify`,
  `speckit.plan`, `speckit.checklist`, `speckit.tasks`, `speckit.analyze`, `speckit.implement`,
  `speckit.converge`, `speckit.taskstoissues`.
- **FR-003**: `.specify/memory/constitution.md` MUST быть заполнен без незаполненных
  плейсхолдеров вида `[ALL_CAPS]` и MUST ссылаться на реальные модули и инварианты проекта.
- **FR-004**: Конституция MUST фиксировать минимум шесть принципов: слоистость, shim-совместимость,
  dry-run для записей, безопасность внешних данных, тесты и quality gate, один worker.
- **FR-005**: Конституция MUST содержать секции технологических ограничений, рабочего процесса
  (включая Definition of Done) и Governance с правилом версионирования по SemVer.
- **FR-006**: Репозиторий MUST содержать работающий baseline-фичу в `specs/001-speckit-baseline/`
  со `spec.md`, `plan.md` и `tasks.md`.
- **FR-007**: Локальный запуск MUST воспроизводиться по шагам из `README.md` на Python 3.10+ и
  приводить к HTTP 200 на `/health` и `/dashboard`.
- **FR-008**: Полный набор маршрутов MUST быть проверен: `/health`, `/health/ready`,
  `/dashboard` и 12 маршрутов `/services/*` отвечают 200.
- **FR-009**: `pytest` MUST проходить полностью; зафиксированный baseline — 263 теста.
- **FR-010**: `ruff check ipsas tests` MUST иметь воспроизводимый набор правил, заданный
  конфигурацией в `pyproject.toml`, независимо от установленной минорной версии ruff.
- **FR-011**: Числовой baseline замечаний линтера MUST быть зафиксирован в конституции и
  сопоставим с текущим выводом.
- **FR-012**: Новые env-переменные MUST появляться одновременно в `.env.example` и
  `DEPLOYMENT.md`; секреты MUST NOT попадать в код, тесты и репозиторий.
- **FR-013**: Изменение архитектуры слоёв, набор маршрутов или списка сервисов UI MUST
  сопровождаться обновлением `STRUCTURE.md` и `QUICKSTART.md` в том же изменении.
- **FR-014**: Правки существующего кода, нарушающего конституцию, MUST оформляться отдельной
  задачей, а не выполняться попутно в несвязанной фиче.
- **FR-015**: `specs/` и `.specify/` MUST коммититься в репозиторий и MUST NOT исключаться
  `.gitignore`.
- **FR-016**: Спецификация фичи MUST содержать приоритетные user stories, измеримые критерии
  успеха и разрешённые `[NEEDS CLARIFICATION]`-пункты вместо выдуманных требований.

### Non-Functional Requirements

- **NFR-001**: Инфраструктура SDD не MUST влиять на рантайм приложения: ни одна зависимость
  из `requirements.txt` / `requirements-dev.txt` не меняется этой фичей.
- **NFR-002**: Открытие каталога `specs/` и запуск команд Spec Kit MUST работать на Windows
  (PowerShell 5.1+) без установки дополнительных рантаймов.
- **NFR-003**: Время полного прогона `pytest` на dev-машине MUST укладываться в 60 секунд.
- **NFR-004**: Скрипты Spec Kit MUST быть идемпотентны: повторный `specify init --here --force`
  не теряет заполненную конституцию.
- **NFR-005**: Документация SDD MUST быть на русском языке, в соответствии с остальной
  документацией проекта.

### Key Entities

- **Конституция** (`.specify/memory/constitution.md`): набор принципов, ограничений и
  критериев готовности проекта; версионируется по SemVer, содержит даты ратификации и
  последней правки.
- **Артефакт фичи** (`specs/<NNN>-<slug>/`): каталог одной работы; содержит `spec.md`
  (что и зачем), `plan.md` (как технически), `tasks.md` (в каком порядке), при необходимости
  `research.md`, `data-model.md`, `contracts/`, `quickstart.md`.
- **Принцип**: именованное нефлексибильное правило со ссылками на модули проекта и
  обоснованием; конфликт «принцип против существующего кода» разрешается в пользу принципа для
  нового кода.
- **Baseline качества**: зафиксированные числа (263 теста, N замечаний ruff) и команды их
  получения; служат точкой отсчёта для сравнения, а не целью «сделать ноль».
- **Окружение разработки**: `.venv` (Python 3.10+), `.env` из `.env.example`, dev-сервер на
  порту `PORT`, каталоги `temp/`, `logs/`, `data/`.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: На чистом клоне развёртывание занимает не более 5 минут и заканчивается
  HTTP 200 на `/health` без ручной правки конфигурации.
- **SC-002**: Все 263 существующих теста проходят; число тестов не уменьшается ни при одной
  будущей фиче без явного обоснования.
- **SC-003**: 14 из 14 проверенных маршрутов (2 health + dashboard + 12 сервисов, `/services/xml-editor`
  после редиректа на канонический URL) отвечают 200.
- **SC-004**: `ruff check ipsas tests` даёт одинаковый результат для любой версии ruff в
  диапазоне `>=0.6.0,<1` — расхождение 0 замечаний.
- **SC-005**: Конституция содержит 0 незаполненных плейсхолдеров и ≥ 6 принципов, каждый из
  которых ссылается минимум на 1 конкретный модуль или инвариант проекта.
- **SC-006**: Описание новой фичи через `/speckit.specify` порождает готовую к ревью
  спецификацию с 3+ приоритетными user stories и ≥ 4 измеримыми критериями успеха.
- **SC-007**: Ни один файл в `.specify/` и `.opencode/` не изменяет рантайм приложения:
  состав `requirements.txt` и `pyproject.toml` (кроме `[tool.ruff]`) идентичен исходному.
- **SC-008**: Время от формулировки намерения до готового к ревью `tasks.md` для типовой
  небольшой фичи — не более 30 минут работы агента.

## Assumptions

- Проект разрабатывается и эксплуатируется внутренним подразделением; авторизация
  обеспечивается периметром (nginx + Basic Auth/ворота сайта), поэтому встроенная
  авторизация в объём SDD-внедрения не входит.
- Таргет — один рабочий процесс: `specify init` один раз, дальше `/speckit.*` в цикле.
  Поддержка нескольких агентов (Claude Code, Cursor) в эту фичу не входит; при необходимости
  `specify init` запускается повторно с `--integration`.
- Локальная разработка ведётся на Windows (PowerShell 5.1), поэтому скрипты Spec Kit установлены
  в варианте `powershell`. Для Linux-команды потребуется `specify init --script sh`, что является
  операционной настройкой, а не изменением репозитория.
- `git clone`/`git pull` из `gl-pub.rcsi.science` работают с системным OpenSSH; глобальная
  настройка `core.sshCommand` уже применена на машине разработчика.
- Базовый runtime — Python 3.11 (`runtime.txt`); наличие только 3.12 на машине разработчика
  приемлемо для dev и тестов и не является блокером.
- Число 1300 замечаний ruff и 53 замечания legacy-набора — существующий долг; его разбор
  вынесен в отдельные задачи, а не в объём этой фичи.
- `pip-audit` прогоняется как часть quality gate, но решение о блокирующем поведении при
  найденных CVE принимается командой, а не автоматически этой фичей.
