# Feature Specification: Лимит загрузки файлов 50 МБ

**Feature Branch**: `004-upload-limit-50mb`

**Created**: 2026-10-05

**Status**: Draft

**Input**: User description: "Нужно увеличить лимит загрузки файлов до 50 Мб."

## Overview

Заказчик просит поднять лимит загрузки до 50 МБ. В коде приложения лимит **уже** равен 50 МБ:
`ipsas/config/settings.py:107` задаёт `MAX_FILE_SIZE` по умолчанию `52428800`, и
`.env.example` содержит те же значения. Тем не менее на развёрнутом экземпляре загрузить файл
больше 12 МБ нельзя, и это не ошибка приложения, а следствие двух мест, оставшихся от старого
лимита 10 МБ:

- `deploy/ipsas.env.production.example:78-79` явно задаёт `MAX_CONTENT_LENGTH` и
  `MAX_FILE_SIZE` по `10485760` (10 МБ). Этот шаблон копируется в `/opt/ipsas/.env` и
  **перекрывает** дефолт в коде: app-лимит на экземпляре равен 10 МБ;
- `deploy/nginx.example.conf:26` задаёт `client_max_body_size 12m`. Этот файл развёрнут как
  `/etc/nginx/sites-available/ipsas.conf` → `/etc/nginx/sites-enabled/ipsas.conf`, поэтому
  nginx отбивает запрос больше 12 МБ с `413 Request Entity Too Large` ещё до того, как
  приложение увидит файл.

Кроме того, `deploy/nginx.example.conf` в комментарии советует держать nginx-лимит `>= 10 МБ`,
то есть документирует старое соглашение. Рассинхрон между nginx-лимитом и app-лимитом не
проверяется ни одним тестом, поэтому он и возник: правка кода ранее подняла app-лимит, а
инфраструктурный слой остался на прежнем значении.

Фича приводит к согласованному состоянию все слои — код, шаблоны окружения, конфигурацию
nginx и документацию — и добавляет автотест, который не даст nginx-лимиту снова отстать.

**Решение по границам (подтверждено владельцем):** 50 МБ — это размер **файла**. Тело
запроса и предел nginx ставятся выше, чтобы служебные байты multipart не съедали лимит. Так,
файл ровно 50 МБ проходит, а `MAX_FILE_SIZE` остаётся равным ровно 50 МБ.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Загрузка файла 50 МБ проходит на развёрнутом экземпляре (Priority: P1)

Редактор загружает через любой сервис UI файл размером до 50 МБ (ZIP рисунков выпуска, архив
ENG-метаданных, XML выпуска) и получает результат обработки, а не ошибку.

**Why this priority**: это и есть запрошенный результат; ради него делается вся фича.

**Independent Test**: на развёрнутом экземпляре загрузка файла ровно 50 МБ через сервис,
который принимает ZIP, завершается успешно; загрузка файла заметно больше 55 МБ отклоняется
понятным сообщением, а не ошибкой сервера.

**Acceptance Scenarios**:

1. **Given** файл размером 50 МБ, **When** он загружается через страницу сервиса,
   **Then** запрос доходит до приложения (nginx не отвечает `413`) и файл принимается.
2. **Given** файл размером 51 МБ, **When** он загружается, **Then** файл отклоняется
   приложением с сообщением о превышении размера, а не падением и не `502`.
3. **Given** файл размером 60 МБ, **When** он загружается, **Then** запрос может быть
   отклонён nginx, но пользователь не видит `500`; отклонение объяснено ограничением размера.
4. **Given** развёрнутый экземпляр, **When** проверяется `docker compose exec ipsas printenv
   MAX_FILE_SIZE MAX_CONTENT_LENGTH`, **Then** значения равны 50 МБ и 55 МБ соответственно.

---

### User Story 2 - Значения лимитов согласованы во всех слоях (Priority: P1)

Значение лимита одинаково во всех местах, где оно задаётся, и ни один слой не перекрывает
другой молча.

**Why this priority**: причина исходного дефекта — именно рассинхрон слоёв; без этого фича
воспроизведётся при следующем изменении лимита.

**Independent Test**: значения `MAX_FILE_SIZE` / `MAX_CONTENT_LENGTH` в `.env.example` и
`deploy/ipsas.env.production.example` совпадают между собой, а `client_max_body_size` в
`deploy/nginx.example.conf` не меньше `MAX_CONTENT_LENGTH`.

**Acceptance Scenarios**:

1. **Given** `deploy/nginx.example.conf`, **When** из него читается `client_max_body_size`,
   **Then** его значение в байтах `>= MAX_CONTENT_LENGTH` из production-шаблона.
2. **Given** `.env.example` и `deploy/ipsas.env.production.example`, **When** сравниваются
   значения лимитов, **Then** `MAX_FILE_SIZE` одинаков и равен 50 МБ, `MAX_CONTENT_LENGTH`
   одинаков и больше него.
3. **Given** код `ipsas/config/settings.py`, **When** ни одна из переменных не задана,
   **Then** `max_content_length` по умолчанию больше `max_file_size`, то есть файл в пределах
   `max_file_size` принимается без срабатывания лимита на тело.

---

### User Story 3 - Расхождение конфигов ломает сборку (Priority: P1)

Ни один слой не может незаметно отстать: рассогласование лимитов выявляется автотестом.

**Why this priority**: это единственная защита от повторения дефекта; ручная сверка трёх файлов
уже однажды не сработала.

**Independent Test**: если уменьшить `client_max_body_size` в `deploy/nginx.example.conf` ниже
`MAX_CONTENT_LENGTH`, `pytest` падает с явным сообщением.

**Acceptance Scenarios**:

1. **Given** автотест лимитов, **When** `client_max_body_size` меньше `MAX_CONTENT_LENGTH`,
   **Then** тест падает и называет оба файла и значения.
2. **Given** автотест лимитов, **When** значения согласованы, **Then** тест проходит.
3. **Given** чистый репозиторий, **When** выполняется `pytest`, **Then** общее число тестов не
   уменьшается относительно baseline на момент фичи.

---

### User Story 4 - Документация объясняет, как изменить лимит (Priority: P2)

Инженер, которому нужно поменять лимит, находит в документации все три места и требуемое
соотношение, а не меняет одно из них наугад.

**Why this priority**: предупреждает повторение рассинхрона через документацию, но не
блокирует запрошенный результат.

**Independent Test**: в `DEPLOYMENT.md` описаны обе переменные и их соотношение, а
`deploy/nginx.example.conf` больше не советует держать nginx-лимит `>= 10 МБ`.

**Acceptance Scenarios**:

1. **Given** `DEPLOYMENT.md`, **When** ищется `MAX_FILE_SIZE`, **Then** переменная описана в
   таблице с пояснением связи с `MAX_CONTENT_LENGTH`.
2. **Given** `deploy/nginx.example.conf`, **When** читается комментарий к
   `client_max_body_size`, **Then** он ссылается на актуальные значения, а не на 10 МБ.
3. **Given** `deploy/SERVER_DEPLOY.md`, **When** ищется симптом «файл не грузится / 413»,
   **Then** в диагностике указаны nginx-лимит и app-лимит как две возможные причины.

---

### Edge Cases

- **Файл ровно на границе лимита.** Если `MAX_CONTENT_LENGTH` равен `MAX_FILE_SIZE`, файл
  размером точно в лимит отклоняется: multipart добавляет к телу запроса служебные байты, и
  срабатывает ограничение на тело, а не на файл. Поэтому тело всегда выше лимита файла.
- **Значение в `m` у nginx.** `client_max_body_size 55m` — это 55 * 1024 * 1024 = 57671680
  байт, то есть мебибайты, а не мегабайты. Совпадение с `MAX_CONTENT_LENGTH` в байтах —
  обязательное условие теста.
- **Забыли перечитать `.env`.** Изменение `MAX_*` требует пересоздания контейнера
  (`docker compose up -d --force-recreate`), иначе приложение продолжит работать со старыми
  значениями.
- **Забыли перезагрузить nginx.** Правка `client_max_body_size` применяется только после
  `nginx -t && systemctl reload nginx`; до этого nginx отбивает запрос по старому лимиту.
- **Несколько полей формы.** Крупные формы с несколькими файлами дают больше служебных байт;
  запас тела запроса покрывает обычный multipart, но не безграничен.
- **Legacy `xml-editor`.** Отдельный каталог `xml-editor/` имеет собственный лимит 20 МБ и в
  production-образ не входит. На текущее развёртывание он не влияет.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: `deploy/ipsas.env.production.example` MUST задавать `MAX_FILE_SIZE=52428800`
  (50 МБ) и `MAX_CONTENT_LENGTH` больше него.
- **FR-002**: `.env.example` MUST содержать те же значения лимитов, что и production-шаблон.
- **FR-003**: `deploy/nginx.example.conf` MUST задавать `client_max_body_size` в байтах не
  меньше `MAX_CONTENT_LENGTH`.
- **FR-004**: `ipsas/config/settings.py` MUST обеспечивать, что при незаданных переменных
  значение `max_content_length` по умолчанию больше `max_file_size` на величину запаса под
  multipart, так что файл размером до `max_file_size` принимается.
- **FR-005**: Репозиторий MUST содержать автотест, который читает
  `deploy/nginx.example.conf`, `deploy/ipsas.env.production.example` и `.env.example` и
  падает при нарушении соотношения «`client_max_body_size` ≥ `MAX_CONTENT_LENGTH` >
  `MAX_FILE_SIZE`».
- **FR-006**: Автотест MUST проверять значение по умолчанию в `settings.py` и его соотношение
  без обращения к сети и без реальных секретов.
- **FR-007**: `DEPLOYMENT.md` MUST описывать `MAX_CONTENT_LENGTH` и `MAX_FILE_SIZE` в таблице
  переменных с указанием связи между ними.
- **FR-008**: Комментарий к `client_max_body_size` в `deploy/nginx.example.conf` MUST
  ссылаться на актуальные значения, а не на 10 МБ.
- **FR-009**: `deploy/SERVER_DEPLOY.md` MUST содержать в диагностике симптом «файл не
  загружается / ошибка 413» с двумя причинами: nginx-лимит и app-лимит.
- **FR-010**: `RAILWAY_DEPLOY.md` MUST содержать согласованные значения лимитов.
- **FR-011**: Изменение MUST NOT удалять и не переименовывать переменные окружения
  `MAX_FILE_SIZE` и `MAX_CONTENT_LENGTH`; их имена — публичный интерфейс.
- **FR-012**: Инструкция по применению на развёрнутом экземпляре MUST требовать перезагрузки
  nginx и пересоздания контейнера, и не требовать пересборки образа, если менялись только
  значения `.env` и конфигурация nginx.

### Non-Functional Requirements

- **NFR-001**: Фича MUST NOT менять состав зависимостей (`requirements*.txt`, `pyproject.toml`).
- **NFR-002**: Автотест MUST быть детерминированным, без сети и без обращения к развёрнутому
  экземпляру; читаются только файлы репозитория.
- **NFR-003**: Значения лимитов MUST храниться в байтах в переменных окружения и в
  человекочитаемой форме в комментариях, без дублирования магических чисел по коду.
- **NFR-004**: Фича MUST NOT затрагивать бизнес-логику сервисов: изменяются конфигурация,
  документация и тесты, но не алгоритмы обработки файлов.
- **NFR-005**: Документация MUST оставаться на русском языке.

### Key Entities

- **`MAX_FILE_SIZE`**: максимальный размер одного загружаемого файла в байтах. Публичное
  значение фичи — `52428800` (50 МБ).
- **`MAX_CONTENT_LENGTH`**: максимальный размер тела HTTP-запроса в байтах; применяется Flask
  и должен превышать `MAX_FILE_SIZE` на запас под multipart.
- **`client_max_body_size`**: предел тела запроса в nginx; должен быть не меньше
  `MAX_CONTENT_LENGTH`. Единица `m` означает мебибайт (1024²).
- **Запас multipart**: разница между пределом тела и лимитом файла; покрывает границы,
  заголовки частей и прочие поля формы.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Автотест лимитов проходит, общее число тестов не меньше baseline на момент
  фичи (320).
- **SC-002**: Значение `MAX_FILE_SIZE` равно 50 МБ одновременно в `.env.example` и
  `deploy/ipsas.env.production.example`.
- **SC-003**: Значение `client_max_body_size` в `deploy/nginx.example.conf` не меньше
  `MAX_CONTENT_LENGTH` в байтах.
- **SC-004**: `max_content_length` по умолчанию в `settings.py` строго больше
  `max_file_size`.
- **SC-005**: В документации и конфигурации нет утверждений о лимитах 10 или 12 МБ,
  кроме исторических артефактов спецификаций; расхождений — 0.
- **SC-006**: Внутренние ссылки Markdown ведут в существующие файлы; битых — 0.
- **SC-007**: На развёрнутом экземпляре файл 50 МБ проходит, файл заметно больше 55 МБ
  отклоняется без `500`.

## Assumptions

- Владелец подтвердил семантику: 50 МБ — это файл; запас тела запроса и nginx берётся
  сверху, конкретное значение запаса (5 МБ) не является предметом согласования.
- Применение на сервере выполняет оператор вручную: правка `.env`, перезагрузка nginx и
  пересоздание контейнера. Автоматического деплоя в проекте нет.
- Значения подобраны для пиковых файлов выпусков (ZIP рисунков, архив ENG-метаданных) и не
  рассчитаны на произвольно большие выгрузки.
- Migration not required: значения переменных не сохраняются в данных, история изменений не
  ведётся.
