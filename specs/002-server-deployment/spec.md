# Feature Specification: Развёртывание IPSAS на внутреннем сервере

**Feature Branch**: `002-server-deployment`

**Created**: 2026-10-02

**Status**: Implemented

**Input**: User description: "Развернуть IPSAS на сервере в Docker Compose, обеспечить доступ по
IP без домена, без TLS и без Basic Auth; обновление вручную через `git pull` и
`docker compose up -d --build`; добавить проверку развёртывания."

> **Происхождение документа.** Спека написана задним числом, после выполнения работы. Работа
> велась без спецификации — это отклонение от конституции, зафиксированное здесь явно. Все
> фактические утверждения ниже проверены на сервере, а не взяты из плана.

## Overview

До этой фичи IPSAS имел инструкции по production только в виде прозы (`DEPLOYMENT.md`) и
варианта «systemd-юнит вручную». Развёрнутых экземпляров не было. Репозиторий содержал
`Dockerfile`, но не содержал ни `docker-compose.yml`, ни шаблона production-конфигурации,
ни образа Nginx-конфигурации, ни способа автоматически проверить живой экземпляр.

Фича вводит готовый к развёртыванию набор: `docker-compose.yml` с публикацией порта только
на loopback и именованными томами, шаблон `.env` для production, конфигурацию reverse-proxy,
пошаговую инструкцию для сервера, smoke-тест для PowerShell и Linux, а также GitLab CI,
запускающий тесты при каждом пуше.

Экземпляр развёрнут на хосте `jourmatproc` и доступен по адресу `http://172.20.254.133/`.
Домен, TLS и авторизация по решению владельца сервиса **не** используются; единственная
защита доступа — приватность адреса.

Код приложения (`ipsas/`, `tests/`) этой фичей не меняется.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Сервис доступен по внутреннему адресу (Priority: P1)

Оператор открывает в браузере внутренний адрес сервера и попадает на дашборд IPSAS, а не на
стандартную страницу Nginx.

**Why this priority**: без доступности фича не имеет смысла — всё остальное обслуживает уже
работающий экземпляр.

**Independent Test**: `curl -I http://172.20.254.133/` на машине во внутренней сети
возвращает `200 OK` с заголовком приложения, а `curl -s http://127.0.0.1:8000/health`
возвращает `{"status":"ok","service":"ipsas"}`.

**Acceptance Scenarios**:

1. **Given** сервер с запущенным контейнером и установленным Nginx, **When** выполняется
   `docker compose ps`, **Then** контейнер `ipsas` имеет статус `running`, а в его логах нет
   ошибок инициализации.
2. **Given** `/etc/nginx/sites-enabled/ipsas.conf` существует как симлинк на
   `sites-available/ipsas.conf`, **When** выполняется `sudo nginx -t` и
   `sudo systemctl reload nginx`, **Then** команда завершается успешно.
3. **Given** активна только конфигурация `ipsas.conf`, **When** выполняется
   `GET http://172.20.254.133/`, **Then** ответ 200 содержит дашборд IPSAS.
4. **Given** экземпляр запущен, **When** выполняется `GET http://127.0.0.1:8000/health`,
   **Then** тело ответа — `{"status":"ok","service":"ipsas"}`.
5. **Given** активна стандартная страница `/etc/nginx/sites-enabled/default`,
   **When** пользователь открывает адрес сервера, **Then** вместо приложения показывается
   `Welcome to nginx!` — это признак неверной конфигурации, а не успешного развёртывания.

### User Story 2 - Обновление экземпляра воспроизводимо (Priority: P1)

Оператор обновляет развёртывание двумя командами и получает именно ту версию кода, что лежит
в репозитории.

**Why this priority**: ручное обновление — единственный способ эксплуатации; его
воспроизводимость важнее любых оптимизаций.

**Independent Test**: после `git pull` и `docker compose up -d --build` страница
`/services/xml-validator` открывается, а внутри образа совпадает текущий commit.

**Acceptance Scenarios**:

1. **Given** экземпляр в рабочем состоянии, **When** выполняется `git pull` и
   `docker compose up -d --build`, **Then** контейнер пересобран и перезапущен, `/health`
   отвечает 200.
2. **Given** обновление выполнено **без** флага `--build`, **When** проверяется версия
   сервиса, **Then** она соответствует предыдущей сборке: Compose переиспользует старый образ
   без ошибки и без предупреждения.
3. **Given** файл `.env` с секретами и именованные тома на месте, **When** выполняется
   `git pull`, **Then** ни `.env`, ни содержимое томов `ipsas-temp` и `ipsas-data`
   не изменяются.
4. **Given** нужно вернуть предыдущую версию, **When** выполняется
   `git checkout <коммит>` и `docker compose up -d --build`, **Then** сервис возвращается на
   прежнюю версию без ручного восстановления данных.

---

### User Story 3 - Конфигурация production корректна и безопасна (Priority: P1)

Экземпляр стартует с набором переменных, при котором формы работают, rate limit не
схлопывается и запись на Платформу остаётся выключенной.

**Why this priority**: три из этих ошибок дают работающий, но непригодный сервис —
тихий 403 на POST-формы или общий лимит запросов на всех пользователей сразу.

**Independent Test**: `docker compose config` проходит проверку, контейнер стартует с
`IPSAS_ENV=production`, а upload XML на `/services/xml-validator` проходит без отказа CSRF.

**Acceptance Scenarios**:

1. **Given** `.env` создан из `deploy/ipsas.env.production.example` и `SECRET_KEY` непустой,
   **When** выполняется `docker compose up -d --build`, **Then** контейнер стартует.
2. **Given** в `.env` пустой `SECRET_KEY` или пустой `ISSUE_FETCH_ALLOWED_HOSTS`,
   **When** выполняется `docker compose up`, **Then** Compose завершается с ошибкой до
   запуска контейнера.
3. **Given** сервис работает по HTTP, **When** в `.env` выставлен
   `SESSION_COOKIE_SECURE=false`, **Then** сессионная cookie принимается браузером и POST-формы
   проходят проверку CSRF. При значении `true` форма отклоняется с ошибкой CSRF.
4. **Given** запрос проходит через Nginx, **When** выставлен `TRUST_PROXY_HEADERS=true`,
   **Then** rate limit считается по адресу клиента из `X-Forwarded-For`, а не по адресу
   Nginx; при выключенном флаге все пользователи делят один лимит 30 запросов в минуту.
5. **Given** несколько Gunicorn workers, **When** отслеживается состояние фоновых задач,
   **Then** очередь и rate limit рассыпаются между процессами; в `docker-compose.yml`
   зафиксирован `GUNICORN_WORKERS=1`.
6. **Given** конфигурация по умолчанию, **When** проверяется `PLATFORM_APPLY_ENABLED`,
   **Then** он равен `0`: запись ENG-метаданных на Платформу остаётся выключенной.
7. **Given** файл с секретами, **When** проверяются права, **Then** он доступен только
   владельцу (`chmod 600`), а `.env` не отслеживается Git.

### User Story 4 - Живой экземпляр проверяется автоматически (Priority: P2)

Оператор может одной командой убедиться, что после развёртывания или обновления работают не
только health-эндпоинты, но и все страницы сервисов.

**Why this priority**: экономит время на ручном обходе 12 страниц при каждом обновлении;
не блокирует первое развёртывание.

**Independent Test**: `bash deploy/smoke-test.sh http://127.0.0.1/` завершается с кодом `0`
и отчётом `17/17`.

**Acceptance Scenarios**:

1. **Given** запущенный экземпляр, **When** выполняется `bash deploy/smoke-test.sh <адрес>`,
   **Then** проверяются `/health`, `/health/ready`, `/dashboard` и маршруты `/services/*`;
   канонический редирект `/services/xml-editor` считается успехом.
2. **Given** экземпляр не запущен, **When** выполняется smoke-тест, **Then** скрипт завершается
   с ненулевым кодом и печатает, какие проверки не прошли.
3. **Given** dev-машина на Windows, **When** выполняется
   `powershell -ExecutionPolicy Bypass -File .\deploy\smoke-test.ps1 -BaseUrl http://127.0.0.1:5000`,
   **Then** набор проверок совпадает с Linux-версией.

---

### User Story 5 - Изменения проверяются до развёртывания (Priority: P2)

Прежде чем код попадёт на сервер, тесты прогоняются автоматически.

**Why this priority**: сервер обновляется вручную, поэтому единственная автоматическая
точка контроля — пайплайн.

**Independent Test**: при пуше в `main` пайплайн создаётся и выполняет `pytest`;
деплой-джобов в пайплайне нет.

**Acceptance Scenarios**:

1. **Given** push в `main`, **When** пайплайн выполняется, **Then** тесты
   (`pytest`) завершаются успешно.
2. **Given** падающий тест, **When** выполняется push, **Then** пайплайн падает и коммит не
   считается проверенным.
3. **Given** пайплайн, **When** просматриваются его джобы, **Then** в нём есть только
   проверка; развёртывание на сервере не выполняется и остаётся ручной операцией.

---

### User Story 6 - Документация соответствует развёртыванию (Priority: P2)

Инженер, получивший репозиторий, может развернуть сервис по документации и не встретит
в ней утверждений, противоречащих действительности.

**Why this priority**: расхождение документации с реальностью — источник неверных
эксплуатационных решений (например, обещание Basic Auth при его отсутствии).

**Independent Test**: каждое утверждение о способе запуска, путях конфигурации и способе
обновления в `README.md`, `DEPLOYMENT.md`, `STRUCTURE.md`, `QUICKSTART.md` и
`deploy/SERVER_DEPLOY.md` соответствует `docker-compose.yml` и фактическому состоянию
сервера; все внутренние ссылки Markdown ведут в существующие файлы.

**Acceptance Scenarios**:

1. **Given** `DEPLOYMENT.md`, **When** ищется описание запуска, **Then** Docker Compose
   указан основным способом, а вариант без Docker помечен как альтернатива.
2. **Given** `DEPLOYMENT.md`, **When** ищется путь к конфигурации, **Then** указан
   `/opt/ipsas/.env` для compose, а не только `/etc/ipsas/ipsas.env`.
3. **Given** `README.md`, `STRUCTURE.md`, `QUICKSTART.md`, **When** перечисляются каталоги
   репозитория, **Then** в них присутствуют `deploy/`, `docker-compose.yml`,
   `.specify/`, `.opencode/` и `specs/`.
4. **Given** `README.md`, **When** ищется описание Spec Kit, **Then** приведены установка и
   команды `/speckit.*`.
5. **Given** любая внутренняя ссылка Markdown в этих документах, **When** она открывается,
   **Then** целевой файл существует.
6. **Given** описание сетевого доступа, **When** читается текст, **Then** в нём прямо сказано,
   что авторизация и TLS отсутствуют.

### Edge Cases

- **Активен стандартный сайт Nginx.** Установленный `nginx` поставляется с
  `/etc/nginx/sites-enabled/default`. Пока он активен, `ipsas.conf` может быть создан
  правильно, но браузер продолжит видеть `Welcome to nginx!`. Проверка `curl -I` по адресу
  сервера — единственный способ отличить эту ошибку от ошибки контейнера.
- **Образ не пересобран.** `docker compose up -d` без `--build` поднимает предыдущий образ без
  предупреждения: пользователь видит работающий сервис на старой версии кода.
- **Docker daemon не запущен.** `docker compose up` падает с ошибкой соединения со сокетом,
  даже если конфигурация верна.
- **Конфликт пакетов Docker.** `docker-compose-plugin` и `docker-compose-v2` конфликтуют при
  установке вместе и оставляют систему без рабочей команды `docker compose`.
- **Пустой `.env` или отсутствие файла.** Compose падает на старте, если `SECRET_KEY` или
  `ISSUE_FETCH_ALLOWED_HOSTS` пусты — это намеренный отказ вместо неработающего сервиса.
- **Права на каталоги данных.** Host bind mount каталога хоста в контейнер ломает права
  непривилегированного пользователя, поэтому используются именованные тома.
- **Порт 8000 занят на хосте.** Публикация порта завершается с ошибкой; при этом сам
  контейнер может быть в статусе `running`.
- **Сервис за прокси без доверия к заголовкам.** Без `TRUST_PROXY_HEADERS=true` все клиенты
  приходят с адреса Nginx и делят один лимит 30 запросов в минуту: сервис выглядит
  «перегруженным» при обычной нагрузке.
- **HTTP вместо HTTPS.** При значении `SESSION_COOKIE_SECURE=true` по умолчанию браузер
  отбрасывает cookie сессии, и все POST-формы получают отказ CSRF при вроде бы исправном
  развёртывании.
- **Рестарт или откат.** Фоновые разборы выпусков в статусе `running` теряются: их состояние
  живёт в `TEMP_DIR` и в памяти процесса.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Репозиторий MUST содержать `docker-compose.yml`, пригодный для production-запуска
  одной командой `docker compose up -d --build`.
- **FR-002**: Порт приложения MUST публиковаться только на loopback хоста
  (`127.0.0.1:8000:8000`); наружу приложение выходит только через reverse-proxy.
- **FR-003**: `TEMP_DIR` и `DATA_DIR` MUST монтироваться именованными томами, а не
  bind mount каталогов хоста.
- **FR-004**: Репозиторий MUST содержать шаблон production-конфигурации
  `deploy/ipsas.env.production.example` без секретов и без значений, пригодных для реального
  доступа.
- **FR-005**: Запуск в production MUST прерываться с понятной ошибкой при пустых `SECRET_KEY`
  или `ISSUE_FETCH_ALLOWED_HOSTS`.
- **FR-006**: Репозиторий MUST содержать конфигурацию reverse-proxy
  `deploy/nginx.example.conf`, публикующую приложение на порту 80, и пошаговую инструкцию
  `deploy/SERVER_DEPLOY.md` по её установке, включая диагностику типовых отказов.
- **FR-007**: Конфигурация развёртывания MUST задавать `GUNICORN_WORKERS=1`,
  `TRUST_PROXY_HEADERS=true` и `SESSION_COOKIE_SECURE=false` для схемы без TLS.
- **FR-008**: Репозиторий MUST содержать smoke-тест живоего экземпляра для Linux
  (`deploy/smoke-test.sh`) и для Windows (`deploy/smoke-test.ps1`), проверяющий health,
  `/dashboard` и маршруты `/services/*`, и завершающийся ненулевым кодом при отказе.
- **FR-009**: Репозиторий MUST содержать `Dockerfile`, собирающий production-образ на
  Python 3.11 и запускающий процесс от непривилегированного пользователя.
- **FR-010**: GitLab CI MUST прогонять `pytest` при каждом пуше и MUST NOT содержать джобы
  развёртывания: обновление сервера остаётся ручной операцией.
- **FR-011**: Документация MUST описывать фактическую схему развёртывания: хост, каталог,
  адрес, способ обновления и обратной отмены.
- **FR-012**: Документация MUST явно указывать отсутствие авторизации и TLS, чтобы отсутствие
  защиты не воспринималось как опечатка.
- **FR-013**: Добавление каталога или файла верхнего уровня MUST сопровождаться обновлением
  дерева каталогов в `STRUCTURE.md`.
- **FR-014**: Новые переменные окружения MUST появляться одновременно в шаблоне production,
  `.env.example` и таблице в `DEPLOYMENT.md`.
- **FR-015**: Скрипты из `deploy/` MUST храниться с окончаниями строк LF, чтобы быть
  исполняемыми на Linux.
- **FR-016**: Секреты MUST NOT попадать в репозиторий: `.env` исключается `.gitignore`,
  шаблон содержит только фиктивные значения.
- **FR-017**: Приложение MUST оставаться доступным по HTTP без TLS: `SESSION_COOKIE_SECURE`
  и CSrf не должны блокировать обычные сценарии работы с сервисами.

### Non-Functional Requirements

- **NFR-001**: Фича MUST NOT менять состав `requirements.txt`, `requirements-dev.txt` и
  рантайм приложения; изменяются только файлы развёртывания, CI и документация.
- **NFR-002**: Ни один модуль `ipsas/` MUST NOT импортировать файлы из `deploy/`:
  инфраструктура развёртывания остаётся вне слоёв приложения.
- **NFR-003**: Скрипты `deploy/*.sh` MUST выполняться в bash без PowerShell и без GNU-расширений,
  недоступных в базовой Ubuntu.
- **NFR-004**: Инструкция развёртывания MUST быть проверяемой на сервере: каждый шаг должен
  приводить к наблюдаемому результату (`docker compose ps`, `curl`, код выхода).
- **NFR-005**: Пайплайн CI MUST быть детерминированным и не требовать секретов для
  выполнения тестов.
- **NFR-006**: Обновление развёртывания MUST требовать не более трёх команд и не более
  обычного времени сборки образа на dev-машине разработчика.
- **NFR-007**: Документация MUST оставаться на русском языке, в соответствии с остальными
  документами проекта.
- **NFR-008**: Состояние, зависящее от памяти процесса (rate limit, очередь фоновых задач),
  MUST NOT выдаваться за долговременное: потеря таких данных при рестарте должна быть описана
  в документации.

### Key Entities

- **Хост** (`jourmatproc`): Ubuntu 24.04 LTS, каталог проекта `/opt/ipsas`, внутренний адрес
  `172.20.254.133`, репозиторий склонирован с read-only deploy key.
- **Compose-проект**: имя `ipsas`, образ `ipsas:latest`, единственный сервис `ipsas`,
  публикация `127.0.0.1:8000`.
- **Том**: именованный том `ipsas-temp` (`TEMP_DIR`) или `ipsas-data` (`DATA_DIR`); переживает
  пересборку образа.
- **Файл окружения** (`/opt/ipsas/.env`): секреты и production-переменные; не отслеживается
  Git; создаётся копированием шаблона.
- **Сайт Nginx** (`ipsas.conf`): симлинк из `sites-enabled` на `sites-available`; единственный
  активный сайт, публикующий порт 80.
- **Smoke-тест**: проверка живоего экземпляра; 17 проверок; ненулевой код выхода при отказе.
- **Пайплайн**: GitLab CI с одной стадией проверки; развёртывание в нём отсутствует.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: `curl -I http://172.20.254.133/` возвращает `200 OK`, а страница содержит
  дашборд IPSAS, а не `Welcome to nginx!`.
- **SC-002**: `curl -s http://127.0.0.1:8000/health` возвращает
  `{"status":"ok","service":"ipsas"}`.
- **SC-003**: `bash deploy/smoke-test.sh http://127.0.0.1/` завершается кодом `0` с
  результатом `17/17`.
- **SC-004**: Порт приложения недоступен с других хостов: попытка обратиться к
  `172.20.254.133:8000` не возвращает ответ приложения.
- **SC-005**: `docker compose config` проходит без ошибок и предупреждений о незаполненных
  переменных.
- **SC-006**: Обновление экземпляра выполняется командой
  `git pull && docker compose up -d --build` и не требует иных ручных действий.

## Assumptions

- Экземпляр используется внутри организации. Адрес `172.20.254.133` приватный и не
  маршрутизируется в интернет; это единственная мера защиты доступа. Решение об отсутствии
  Basic Auth и TLS принято владельцем сервиса осознанно.
- Обслуживание выполняет один оператор с доступом по SSH. Автоматическое развёртывание не
  требуется и сознательно не делается: GitLab CI остаётся test-only.
- Обновление выполняется вручную из `/opt/ipsas` командой `git pull`, за которой следует
  `docker compose up -d --build`. Автоматические пуши в репозиторий не выполняются.
- Сервис работает с одним Gunicorn worker. Увеличение числа workers потребует выноса
  rate limit и очереди задач из памяти процесса — это отдельная работа.
- `/etc/ipsas/ipsas.env` и systemd-юнит сохранены как альтернативный способ запуска для хостов
  без Docker, но в текущем развёртывании не используются.
- Внутренний IP фиксирован. Смена адреса требует правки Nginx и документации.
- Docker Engine 29.x и Compose v2 на сервере установлены и поддерживаются; приведённые
  версии проверены на момент развёртывания.
