# Implementation Plan: Развёртывание IPSAS на внутреннем сервере

**Branch**: `002-server-deployment` | **Date**: 2026-10-02 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/002-server-deployment/spec.md`

> **Происхождение документа.** План и задачи написаны задним числом, по факту выполненной
> работы. Порядок фаз ниже отражает фактическую последовательность, а не проектирование.

## Summary

Сделать IPSAS развёртываемым на внутреннем сервере и задокументировать развёртывание так,
чтобы оно соответствовало реальности. Технический подход: Docker Compose публикует порт
приложения только на loopback, наружу приложение выходит через Nginx на порту 80; секреты и
production-переменные живут в `/opt/ipsas/.env`, созданном из шаблона в репозитории; состояние,
которое не должно переживать пересборку, вынесено в именованные тома; проверка живого
экземпляра автоматизирована smoke-тестом; тесты в пайплайне остаются единственной
автоматической точкой контроля.

Домен, TLS и авторизация не добавляются. Обновление экземпляра — ручная операция из двух
команд. Код приложения и состав зависимостей не меняются.

## Technical Context

**Language/Version**: Python 3.11 внутри образа (совпадает с `runtime.txt`); сборка
`python:3.11-slim`. Скрипты развёртывания — bash (Linux) и PowerShell 5.1 (Windows).

**Primary Dependencies**: зависимости приложения не меняются. Добавляется инфраструктура:
Docker Engine 29.x, Docker Compose v2 (на сервере 29.8.2 / 2.40.3), Nginx (Ubuntu 24.04).

**Storage**: файлы в `TEMP_DIR` и `DATA_DIR`, смонтированные именованными томами `ipsas-temp`
и `ipsas-data`. БД нет. Rate limit и очередь фоновых задач — в памяти процесса.

**Testing**: `pytest` (263 теста, baseline не уменьшается); `docker compose config`;
shell-проверка скриптов; smoke-тест живого экземпляра (17 проверок); ручная проверка
`curl -I` по адресу сервера для отделения ошибок Nginx от ошибок контейнера.

**Target Platform**: dev — Windows/PowerShell; production — Linux (Ubuntu 24.04), Docker
Compose + Nginx, один Gunicorn worker.

**Project Type**: web-service (Flask, Jinja2, без сборки фронтенда).

**Performance Goals**: один worker (`GUNICORN_WORKERS=1`); `RATE_LIMIT_PER_MINUTE=30`;
`MAX_CONCURRENT_JOBS=4`, `MAX_JOB_QUEUE=8`; ответ health-эндпоинта — единицы миллисекунд.

**Constraints**: без БД; без встроенной авторизации; один worker gunicorn; `SECRET_KEY`
обязателен в production; `ISSUE_FETCH_ALLOWED_HOSTS` обязателен в production; CSRF включён;
`PLATFORM_APPLY_ENABLED=0` по умолчанию; сервис работает по HTTP, поэтому
`SESSION_COOKIE_SECURE=false`.

**Scale/Scope**: 11 новых файлов развёртывания и CI, 0 изменений в `ipsas/`, 0 изменений в
`requirements*.txt`. Один сервер, один экземпляр, один оператор.

## Implementation Phases

### Phase 0: Образ и окружение запуска

Сделать контейнер пригодным для production: непривилегированный пользователь, отсутствие
кэша pip в слоях, фиксация версии. Проверяется сборкой образа.

### Phase 1: Docker Compose

Основной артефакт фичи. Публикация порта только на `127.0.0.1`, именованные тома для
`TEMP_DIR` и `DATA_DIR`, обязательные переменные окружения с проверкой на пустоту,
`GUNICORN_WORKERS=1`, healthcheck. Проверяется `docker compose config`.

### Phase 2: Конфигурация приложения для реального запуска

Выявить три настройки, которые делают работающий сервис непригодным: `SESSION_COOKIE_SECURE`
(формы отклоняются по CSRF на HTTP), `TRUST_PROXY_HEADERS` (весь трафик попадает в один
лимит rate) и `GUNICORN_WORKERS` (рассыпается очередь задач). Зафиксировать их в шаблоне
`.env` и описать последствия ошибки в документации.

### Phase 3: Nginx и инструкция развёртывания

Шаблон `nginx.example.conf` и пошаговый документ. Отдельно описать диагностику: почему
активна стандартная страница `nginx` и как отличить ошибку прокси от ошибки контейнера.

### Phase 4: Проверка живого экземпляра

Smoke-тест для Linux и Windows: health, `/dashboard`, маршруты `/services/*`, учёт
канонического редиректа. Ненулевой код выхода при отказе.

### Phase 5: Автоматическая проверка изменений

`.gitlab-ci.yml` с единственной стадией тестов. Джобов развёртывания нет — это осознанное
ограничение, а не недоработка.

### Phase 6: Развёртывание на сервере

Подготовка хоста, клонирование репозитория, создание `.env`, запуск Compose, установка и
подключение Nginx. Фиксируется выявленная проблема: стандартный сайт Nginx отображается
раньше конфигурации IPSAS и перекрывает её.

### Phase 7: Аудит документации

Синхронизировать `README.md`, `DEPLOYMENT.md`, `STRUCTURE.md`, `QUICKSTART.md` с фактическим
развёртыванием. Выявлено 10 расхождений, все — несоответствие документации развёртыванию,
а не дефект развёртывания.

## Verification Strategy

| Что | Как проверяется | Результат |
|-----|-----------------|-----------|
| Схема Compose валидна | `docker compose config` | без ошибок и предупреждений |
| Контейнер запускается | `docker compose ps`, логи | статус `running`, без ошибок инициализации |
| Приложение отвечает локально | `curl -s http://127.0.0.1:8000/health` | `{"status":"ok","service":"ipsas"}` |
| Приложение отвечает снаружи | `curl -I http://172.20.254.133/` | `200 OK`, содержимое — дашборд IPSAS |
| Порт приложения закрыт | обращение к `172.20.254.133:8000` | нет ответа приложения |
| Все страницы живы | `bash deploy/smoke-test.sh http://127.0.0.1/` | `17/17`, код выхода `0` |
| Формы работают на HTTP | загрузка XML на `/services/xml-validator` | без отказа CSRF |
| Регрессий нет | `pytest` | не менее 263 тестов |
| Документация верна | сверка утверждений с `docker-compose.yml` и состоянием сервера | 0 расхождений |

## Risks & Trade-offs

- **Отсутствие авторизации и TLS — осознанный риск.** Любой, кто достигнет приватного адреса
  из внутренней сети, получает доступ ко всему сервису, включая операции от имени редактора
  Платформы. Принято по решению владельца сервиса; митигация — приватность адреса и отсутствие
  маршрутизации в интернет. Порог для пересмотра: появление публичного доступа или доступ из
  сетей, не являющихся доверенными.
- **Отсутствие автоматического развёртывания.** Обновление вручную: ошибка оператора возможна,
  автоматической проверки «на сервере та же версия, что в репозитории» нет. Митигация —
  smoke-тест в наборе команд обновления.
- **`git pull` без `--build` даёт работающий старый сервис.** Ошибка не проявляется
  сообщением. Митигация — явное указание в `README.md`, `DEPLOYMENT.md` и `SERVER_DEPLOY.md`.
- **Стандартный сайт Nginx перекрывает конфигурацию IPSAS.** Ошибка выглядит как «сервис не
  заработал», хотя контейнер исправен. Митигация — отдельный раздел диагностики и проверка
  `curl -I` перед обращением к логам контейнера.
- **In-memory состояние.** Rate limit и очередь фоновых задач теряются при рестарте и
  рассыпаются при нескольких worker'ах. Митигация — фиксированный `GUNICORN_WORKERS=1` и
  явное описание последствий. Устранение полностью требует отдельной работы.
- **`pip-audit` не блокирует.** Уязвимости в зависимостях фиксируются, но не блокируют
  сборку: решение о блокирующем поведении остаётся за командой.

## Future Work

- HTTPS и Basic Auth или IP allowlist в Nginx — при выходе за пределы доверенной сети.
- Автоматическое развёртывание (джоб после тестов) — при готовности менять модель
  «обновление вручную».
- Вынос rate limit и очереди задач из памяти процесса — предварительное условие для
  `GUNICORN_WORKERS > 1` и горизонтального масштабирования.
- Резервное копирование томов `ipsas-temp` и `ipsas-data` — сейчас содержимое переживает
  пересборку образа, но не восстанавливается после потери хоста.

## Notes

- Работа выполнена в обход процесса: спецификация, план и задачи написаны после того, как
  развёртывание уже работало. Все утверждения в артефактах проверены на сервере; расхождение
  между планом и фактом отмечено явно, а не переписано задним числом.
- Значения из шаблона `.env` фиктивны; реальный `SECRET_KEY` создан на сервере и в репозиторий
  не попадает.
