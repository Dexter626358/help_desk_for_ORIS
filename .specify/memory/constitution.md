# IPSAS Constitution

Внутренний сервис **IPSAS** (Internal Publishing Support System, репозиторий исторически
`help_desk_for_oris`) — Flask-приложение без БД и авторизации для обработки журнальных
материалов: XML/XSD, библиография, метаданные выпусков, PDF/CSV, операции на платформе OJS.

## Core Principles

### I. Слоистость: логика живёт в домене, не в маршрутах

Направление зависимостей строго одно: `ipsas/web` → `ipsas/services` → `ipsas/modules` →
`ipsas/common`, фоновые задачи — `ipsas/jobs`.

- Blueprint-маршрут содержит только: чтение/валидацию формы, вызов одного сервиса,
  `flash`/редирект или отдачу файла. Бизнес-логики, регулярных выражений, разбора XML и
  HTTP-вызовов в маршрутах быть не должно.
- Исходящий HTTP из доменного слоя изолируется в отдельном модуле (образец:
  `ipsas/modules/issue_metadata/http_client.py`). Новый сетевой клиент создаётся по этому
  образцу, а не внутри валидатора или парсера.
- Публичный API доменного модуля объявляется в `__init__.py.__all__`; потребители импортируют
  пакет, а не внутренние файлы пакета.
- Обоснование: 12 сервисов UI и 155 модулей уже разведены по слоям. Возврат логики в
  `ipsas/web/*` разрушает тестируемость домена и делает миграцию старых путей на новые
  невозможной.

### II. Обратная совместимость через shim, а не удаление

Старые пути (`journal_xml_analyzer`, `journal_xml_report/`, `reference_*`, `validator`,
`issue_metadata_parser`, `issue_metadata_tasks`, `xsd_validator`, …) не удаляются.

- Перенос реализации выполняется созданием shim-модуля с докстрокой
  `"""Compatibility shim → ``ipsas.modules.<target>``."""` и явным `__all__`
  (либо star-reexport с переносом `__all__` и `# noqa: F403`).
- Shim не содержит собственной логики, кроме случаев, где старый контракт отличался
  от нового (тогда расхождение описано в докстринге).
- `DeprecationWarning`/`warnings.warn` в пакете `ipsas` не используются: внешние
  потребители (внутренние скрипты, выгрузки) не должны получать шум.
- CLI-контракт (`python -m ipsas.cli …`, `ipsas-web`) и имена env-переменных — публичный
  интерфейс; их изменение требует явной строки в плане и обновления `README.md`,
  `QUICKSTART.md`, `DEPLOYMENT.md`.
- Обоснование: shim-слой — осознанное решение проекта, зафиксированное в `STRUCTURE.md`.

### III. Dry-run по умолчанию для любых записей во внешние системы

Операции, меняющие платформу (OJS/Платформа/песочница), по умолчанию только читают.

- Запись разрешается исключительно при явном opt-in: `PLATFORM_APPLY_ENABLED=1` для
  ENV-сервисов либо флагом `--apply` / снятой галочкой в UI.
- Новый сервис с записью обязан иметь тот же переключатель, а также путь «показать, что
  будет сделано» до записи.
- `ISSUE_FETCH_ALLOWED_HOSTS` обязан содержать хост целевой системы; иначе SSRF-слой
  отклонит запрос.
- Обоснование: ошибка в этих сценариях затрагивает живой выпуск и учётные записи
  редактора; цена отката несопоставима с ценой лишнего шага.

### IV. Внешние данные недоверенные: SSRF, XML, ZIP, CSRF

Любой вход извне (загруженный файл, введённый URL, ZIP-архив, содержимое удалённой
страницы) обрабатывается только через существующие защитные примитивы.

- Исходящие URL — только через `ipsas.common.ssrf` (`assert_safe_fetch_url`,
  `urlopen_safe`, `is_safe_fetch_url`) и белый список `ISSUE_FETCH_ALLOWED_HOSTS`.
  Редиректы проверяются в том числе (`tests/test_production_hardening.py`).
- XML разбирается только `ipsas.common.xml_secure.create_secure_parser`
  (без внешних сущностей, без `resolve_entities`).
- ZIP распаковывается только `ipsas.common.zip_safe.extract_zip_safely`
  (лимиты `ZipLimits`, проверка `safe_member_path`, защита от Zip Slip).
- CSRF включён для POST-форм; `IPSAS_DISABLE_CSRF` в `IPSAS_ENV=production` приводит к
  `RuntimeError` на старте, а не к предупреждению.
- Детали исключений не попадают в UI: глобальный обработчик отдаёт нейтральный текст и
  `request_id`, детали — только в лог. Прямое включение `str(exc)` в `flash` допускается
  лишь в web-слое и не должно раскрывать секреты, пути и учётные данные.
- Секреты (`PLATFORM_PASSWORD`, `SANDBOX_*_PASSWORD`, `SECRET_KEY`) задаются только
  переменными окружения; `.env` не коммитится (уже в `.gitignore`).
- Обоснование: сервис без собственной авторизации полностью полагается на периметр;
  единственная защита от SSRF/XXE/Zip Slip — код.

### V. Тесты и quality gate

- `pytest` обязателен: 263 теста — baseline, его нельзя уменьшать молча.
- Тесты детерминированы: без сети, без реальных учётных данных, без зависимости от
  порядка; сеть — только через `monkeypatch`/подставной клиент.
- Каждый новый доменный сценарий покрывается в `tests/` файлом, названным по домену
  (`test_<domain>.py`); для нового маршрута — проверка статуса и ключевого содержимого
  ответа.
- `ruff check ipsas tests` и `pip-audit -r requirements.txt` прогоняются перед сдачей.
- Известный долг (зафиксирован на 2026-09-28, не является поводом «поправить попутно»):
  - с `ruff 0.16.9` и его расширенными default-наборами — 1300 замечаний;
  - с legacy-набором `E4,E7,E9,F` — 53 замечания.
  `pyproject.toml` не содержит `[tool.ruff]`, поэтому фактический набор правил зависит от
  установленной версии. Любое изменение линтера требует отдельной спецификации.
- Обоснование: единственный автоматический контроль качества в проекте — pytest и ruff;
  отсутствие явной конфигурации ruff делает baseline нестабильным.

### VI. Один процесс: in-memory состояние

`GUNICORN_WORKERS=1` — не настройка по умолчанию, а требование корректности.

- Лимит одновременных задач, очередь фоновых задач, rate limit и активные locks
  хранятся в памяти процесса. Второй worker создаёт вторые независимые лимиты.
- Секреты, состояние задач и временные файлы не переживают перезапуск; это осознанное
  ограничение, а не дефект.
- `IPSAS_ENV=production` обязан валидировать инварианты на старте: задан `SECRET_KEY`,
  `FLASK_DEBUG` выключен, `ISSUE_FETCH_ALLOWED_HOSTS` непуст.

## Технологические ограничения

- Python 3.11 (`runtime.txt`); `pyproject.toml` допускает `>=3.10`. Локальная разработка
  и тесты проверены на 3.12.
- Пин диапазонов обязателен: `Flask>=3.0.0,<3.2`, `Werkzeug>=3.0.0,<3.2`,
  `Flask-WTF>=1.2.0,<2`, `WTForms>=3.0.0,<4`, `lxml>=6.1,<7`, `pypdf>=3.9,<7`,
  `gunicorn>=21.2.0,<24`. Новые зависимости требуют обоснования в плане и обновления
  `requirements.txt` **и** `pyproject.toml` синхронно.
- Архитектурно: без БД, без встроенной авторизации, состояние — файлы в `TEMP_DIR`
  плюс память процесса. Введение БД — отдельная спецификация с миграционным планом.
- Стиль: `snake_case` для модулей, `PascalCase` для классов, `UPPER_SNAKE` для констант,
  `_`-префикс для приватных функций и констант, `from __future__ import annotations` в
  новых модулях. Новый код — на современных аннотациях (`dict[str, Any]`); legacy
  `typing.Dict/Optional` не расширяется.
- Логирование — только через `ipsas.utils.logger.get_logger`; сообщения через
  `%`-аргументы, исключения через `exc_info=True` (в web) или `logger.exception`
  (глобальный обработчик).
- Иерархия ошибок — `ipsas.common.exceptions.IpsasError` и наследники; трансляция
  внешних исключений выполняется с `raise ... from exc`.
- Пользовательские тексты, отчёты и письма редакции — на русском языке, литералами в коде;
  i18n-каталога в проекте нет.
- Документация обязательна к правке вместе с кодом: `README.md` (назначение, запуск),
  `STRUCTURE.md` (слои, модули, blueprints), `QUICKSTART.md` (сервисы UI),
  `DEPLOYMENT.md` (production, env, Docker, systemd), `.env.example` (переменные).

## Рабочий процесс и критерии готовности

Работа ведётся по Spec-Driven Development: спецификация → план → задачи → реализация.

- Одна фича — один каталог `specs/<NNN>-<slug>/` со своей `spec.md`, `plan.md`,
  `tasks.md`, `research.md`, `data-model.md`, `contracts/`, `quickstart.md`.
- Изменения кода без зафиксированной спецификации не принимаются; для точечных правок
  допускается `specs/<NNN>-quick-fix/`.
- Последовательность команд: `/speckit.specify` → `/speckit.clarify` (по необходимости) →
  `/speckit.plan` → `/speckit.checklist` → `/speckit.tasks` → `/speckit.analyze` →
  `/speckit.implement`.
- Определение готовности (Definition of Done):
  1. `pytest` — все тесты проходят, новые покрывают добавленное поведение.
  2. `ruff check ipsas tests` — новых замечаний не добавлено (сверка с baseline).
  3. `GET /health` и `GET /health/ready` отвечают 200, затронутые маршруты отвечают 200.
  4. Новые env-переменные отражены в `.env.example` и `DEPLOYMENT.md`; секретов в коде нет.
  5. Обновлена затронутая документация; `STRUCTURE.md` актуален при изменении слоёв.
  6. Для UI-изменений — ручная проверка затронутого сценария, а не только тест.
- Коммиты: сообщение в стиле репозитория (`fix(web): …`, `add serves archive …`),
  одна логическая единица работы; коммит spec-артефактов допускается вместе с кодом.

## Governance

- Конституция имеет приоритет над устными договорённостями и над привычками, принесёнными
  из других проектов. При конфликте «конституция против существующего кода» побеждает
  конституция для нового кода; существующий код приводится к ней отдельной задачей, а не
  попутно.
- Поправки: предлагаются как изменение этого файла с обоснованием и планом миграции;
  версия повышается по SemVer — MAJOR при снятии или переопределении принципа, MINOR при
  добавлении принципа или расширении требований, PATCH при уточнении формулировок.
- Проверка соответствия выполняется в `/speckit.plan` (план обязан ссылаться на
  нарушаемые принципы) и в `/speckit.analyze` (согласованность артефактов).
- `sync impact report` (HTML-комментарий в начале файла) — временный материал для
  ревью поправки и удаляется до коммита.
- Амортизация долга: известные нарушения (53 замечания ruff, отсутствие
  `[tool.ruff]`, отсутствие автоматической проверки границ слоёв) фиксируются как задачи,
  а не исправляются в рамках несвязанных фич.
