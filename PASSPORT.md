## §1. Карточка

**Название:** IPSAS — Internal Publishing Support System

**Что это.** Внутренний веб-инструмент редактора издательства: веб-интерфейсы для работы
с XML журналов, библиографией, выпусками и метаданными. Репозиторий исторически называется
`help_desk_for_oris`.

**Статус:** в эксплуатации. Экземпляр развёрнут, smoke-тест проходит 17/17.

**Репозиторий:** `git@gl-pub.rcsi.science:other-web-applications/help_desk_for_oris.git`,
ветка `main`, развёртывание вручную из неё.

**Владелец:** `___ЗАПОЛНИТЬ: ФИО или роль___`

**Связанные системы:** Платформа (OJS), песочница `f23g45.rcsi.science`, НППНИ.

### Три вещи, которые нужно знать до работы с сервисом

**1. Авторизации нет вообще.** Ни логина, ни пароля, ни ролей. Любой, кто достигнет
приватного адреса из внутренней сети, получает доступ ко всему функционалу, включая
операции от имени учётной записи редактора на Платформе. Единственная защита — приватность
адреса: `172.20.254.133` не маршрутизируется в интернет.

*Проверено: чтением кода — механизмы аутентификации в `ipsas/web/` отсутствуют; в
`config/settings.py` нет ни одной переменной пользователя или пароля.*

Порог для пересмотра решения: появление публичного доступа или доступ из сетей, не являющихся
доверенными. Тогда нужны HTTPS и Basic Auth либо IP allowlist в nginx.

**2. Сервис не является источником данных.** Базы данных нет. Всё, что через него проходит,
происходит из Платформы. Потеря хоста означает потерю времени редактора, а не публикационных
данных. Подробности — §4 и §5.

**3. TLS нет.** Только HTTP. Внутренний адрес не маршрутизируется в интернет, но канал нужно
считать открытым.

**4. Запись в ОПУС включена.** На развёрнутом экземпляре `PLATFORM_APPLY_ENABLED=1` —
форма «Обновить ENG-метаданные» выполняет настоящий POST под учётной записью `gsn`. Отправить
его повторно и откатить нельзя: изменение уже на стороне ОПУС. По умолчанию в коде запись
выключена, но здесь она разрешена осознанно.

*Проверено 2026-10-05: `docker compose exec ipsas printenv PLATFORM_APPLY_ENABLED` → `1`.*

## §3. Технические данные

### Визитка

| | |
|---|---|
| Язык | Python 3.11 в контейнере; `pyproject.toml` допускает 3.10+ |
| Веб-фреймворк | Flask 3.0–3.2, Werkzeug 3.x |
| Формы и CSRF | Flask-WTF 1.2, WTForms 3.x |
| XML | lxml 6.x, схема `schemas/journal3.xsd` |
| PDF | pypdf 3.9–7 |
| WSGI-сервер | gunicorn 21.2–24, **всегда 1 worker** |
| Хранилище | файлы на диске + память процесса. **БД нет** |
| Контейнер | `python:3.11-slim`, непривилегированный пользователь uid 10001 |
| Прокси | nginx, порт 80 |
| Объём кода | 171 файл, ~33 600 строк в `ipsas/`; 31 файл тестов, ~6 300 строки |
| Тесты | 320, `pytest` |
| Маршруты | 15 blueprint'ов под `/services` + `xml_editor` со своим префиксом + `main` |

### Компоненты

Слои выстроены сверху вниз, зависимости идут только вниз:

```
HTTP        ipsas/web/            Flask, blueprint'ы, CSRF, rate guard, health
Сценарии    ipsas/services/       что делает каждая страница
Домен       ipsas/modules/        бизнес-логика по доменам: journal_xml, bibliography,
                                   issue_metadata, eng_metadata, archive_by_sender,
                                   issue_supp_images, journal_site, sandbox_journal_setup,
                                   pdf_matching, metafora_jats, xml_validator, xml_editor
Общее       ipsas/common/         validation, ssrf, zip_safe, xml_secure, models, exceptions
Задачи      ipsas/jobs/           файловый статус фоновых задач
Конфиг      ipsas/config/         settings.py: разбор окружения и production-проверки
```

**Legacy-shim'ы.** Старые пути импорта (`journal_xml_analyzer`, `journal_xml_report/`,
`reference_*`, `validator`, `issue_metadata_parser`, `web/issue_metadata_tasks`) сохранены
как тонкие обёртки. Новый код импортирует только по новым путям; shim'ы не удаляются без
отдельного решения. Это принцип II конституции проекта.

**Статусы фоновой задачи:** `queued` → `running` → (`done` | `error`). При старте сервера
задачи в статусе `running` помечаются как прерванные — они не восстанавливаются.

### Интеграции

Все исходящие. IPSAS ничего не принимает извне, кроме файлов, загруженных редактором.

| Система | Назначение | Учётная запись | Режим записи |
|---------|-----------|----------------|--------------|
| Платформа (OJS) | запись ENG-метаданных | `gsn` | **включена** (`PLATFORM_APPLY_ENABLED=1`) |
| Платформа (OJS) | архивация «Новые», рисунки выпуска | `gsn` | по умолчанию dry-run, на форме снимается галочка |
| Песочница `f23g45` | базовая настройка журнала | `developer` | по умолчанию dry-run, флаг `--apply` |
| Журналы OJS / НППНИ | разбор опубликованного выпуска по URL | без логина | только чтение |

*Проверено 2026-10-05: `docker compose exec ipsas printenv PLATFORM_APPLY_ENABLED PLATFORM_USERNAME` → `1`, `gsn`.*

**Принципы интеграций:**

- Все исходящие запросы проходят через SSRF-защиту: хосты из `ISSUE_FETCH_ALLOWED_HOSTS`
  (в production — обязательная переменная), блокируются localhost, приватные адреса и
  редиректы на них. На экземпляре: `journals.rcsi.science,f23g45.rcsi.science`.
- Все операции записи по умолчанию — dry-run. Запись включается явным флагом на форме
  или `--apply` в CLI. Глобальный флаг `PLATFORM_APPLY_ENABLED` управляет только
  ENG-метаданными: архивация и рисунки под него не попадают.
- Пароль учётной записи редактора передаётся платформе, поэтому доступ к самому IPSAS нужно
  ограничивать не слабее, чем доступ к Платформе.
- Применённое значение `PLATFORM_APPLY_ENABLED` — свойство экземпляра, а не репозитория.
  Значение по умолчанию в коде — `0`; здесь — `1`. Отправленный POST необратим.

## §4. Инфраструктура

| | |
|---|---|
| Хост | `jourmatproc`, Ubuntu 24.04 LTS |
| Адрес | `172.20.254.133` — приватный, из интернета недоступен |
| Каталог | `/opt/ipsas`, клон репозитория |
| Docker | Engine 29.8.2, Compose v2.40.3 |
| Прокси | nginx, слушает порт 80, проксирует на `127.0.0.1:8000` |
| Тома | `ipsas-temp` (`TEMP_DIR`), `ipsas-data` (`DATA_DIR`) |
| Секреты | `/opt/ipsas/.env`, права `600`, не в Git |
| Экземпляров | один |
| Резервных копий | **нет** |
| Сертификатов | **нет** — TLS не используется |
| Мониторинга | **нет** |

**Почему тома именованные, а не каталоги хоста:** контейнер работает от
непривилегированного пользователя, и bind mount каталога хоста даёт неверные права внутри
контейнера — загрузка файлов падает.

**Почему порт приложения закрыт на loopback:** единственная точка входа — nginx. Публикация
`8000` на всех интерфейсах открыла бы сервис в обход прокси.

**Про сертификаты.** Раздел пуст не по недосмотру: сервис работает по HTTP, TLS-сертификаты
не нужны. Если сервис станет доступен за пределами доверенной сети, понадобится HTTPS в nginx
плюс собственная система выпуска сертификатов — сейчас её нет.

## §5. Эксплуатация

### Мониторинг и логи

Системы мониторинга и оповещений **нет**. Алертов не приходит — молчание сервиса не означает,
что он работает.

Что есть:

- В production логи идут в stdout, файл отключён:
  `docker compose logs -f ipsas`
- Каждый ответ с ошибкой содержит `request_id`; он же попадает в запись лога. Это главный
  инструмент поиска: по `request_id` находится конкретный запрос.
- `request_id` принимается из заголовка `X-Request-Id`, если его прислал прокси, иначе
  генерируется.
- Health-эндпоинты: `/health`, `/health/live`, `/health/ready` (готовность: доступна запись
  во временный каталог и на месте XSD).
- Аутентифицированных метрик нет, `/metrics` не существует.

*Проверено: чтением `ipsas/web/app.py` — `request_id` в `g.request_id`, в ответах об ошибке и
в записях лога; `ipsas/web/routes.py` и `app.py` — три health-эндпоинта.*

**Порог для пересмотра:** если сервис признать критичным, нужен внешний опрос `/health` и
сбор логов nginx в коллектор. До этого единственный способ узнать об отказе — зайти и
проверить.

### CI, деплой и откат

**CI.** GitLab CI, единственная стадия `test`:

| Джоб | Команда | Блокирует? |
|------|---------|-----------|
| `pytest` | `pytest -q --junitxml=reports/junit.xml` | да |
| `ruff` | `ruff check . \|\| true` | нет, предупреждение |
| `pip-audit` | `pip-audit -r requirements.txt \|\| true` | нет, предупреждение |

Линтер и аудит зависимостей не блокируют пайплайн сознательно: в коде есть давние
замечания, и их не стоит чинить попутно.

> **Не подтверждено:** пайплайн создан и проверен на синтаксис, но факт его фактического
> выполнения на инстансе GitLab не наблюдался. До первого прогона не считать, что плохой
> коммит отсекается автоматически.

Конфигурация ruff в `pyproject.toml` отсутствует, поэтому набор правил зависит от версии
линтера: 53 замечания при `--select E4,E7,E9,F` против 1300 при default-наборе. Открытое
решение команды, задача T046 в
[specs/001-speckit-baseline/tasks.md](specs/001-speckit-baseline/tasks.md).

**Деплой — ручной, три команды на сервере:**

```bash
cd /opt/ipsas
git pull
docker compose up -d --build
bash deploy/smoke-test.sh http://127.0.0.1/
```

Флаг `--build` обязателен: код находится внутри образа, и без пересборки поднимется
предыдущая версия **без ошибки и без предупреждения**.

При изменении только `.env` пересборка не нужна, но контейнер требуется пересоздать —
переменные окружения читаются только при создании:

```bash
docker compose up -d --force-recreate
```

`.env` и тома при `git pull` не затрагиваются.

**Откат:**

```bash
cd /opt/ipsas
git checkout <предыдущий-коммит>
docker compose up -d --build
```

**Почему деплой не автоматизирован:** решение владельца. Обратная сторона — ошибка оператора
возможна, и автоматической проверки «на сервере та же версия, что в репозитории» не
существует. Взамен есть smoke-тест из 17 проверок.

### Резервное копирование

**Резервных копий не делается.** Процедуры и расписания нет.

Что теряется при уничтожении хоста:

| Данные | Восстановимость |
|--------|-----------------|
| загруженные редактором XML и PDF | повторной загрузкой из Платформы |
| сгенерированные отчёты и письма | повторной генерацией |
| состояние фоновых задач, включая незавершённые разборы выпусков | **не подлежит восстановлению** |
| работоспособность сервиса | развёртыванием заново |

Сервис не является источником данных: всё, что через него проходит, происходит из Платформы.
Отсутствие бэкапов означает потерю времени редактора, а не потерю публикационных данных.

### Инциденты и SLA

**Формализованного SLA нет.** Не определены: время реакции, время восстановления, окно
обслуживания, каналы обращения.

Практически: дежурного и графика дежурств нет, сервис обслуживает один оператор.
Отсутствие оповещений означает, что отказ обнаруживается жалобой пользователя.

Ближайший шаг, если сервис признать критичным: зафиксировать SLA на восстановление и
добавить опрос health-эндпоинта.

## §6. Процессы и репозиторий

**Статус процессов внедрения.** В репозитории развёрнут Spec Kit (Spec-Driven Development).
Конституция и три спецификации зафиксированы: внедрение процесса, развёртывание на сервере,
технический паспорт.

**Ветки и релизы.** Основная ветка `main`. Теги не используются. Релиз — это состояние
`main` плюс пересобранный образ на сервере; автоматической привязки нет, поэтому
соответствие версии сервера репозиторию проверяется вручную.

**Проверки перед merge:**

1. `pytest` проходит локально — 263 теста.
2. `pytest` зелёный в пайплайне.
3. Изменение окружения или маршрутов отражено в документации в том же изменении.
4. Операция записи по умолчанию остаётся dry-run.
5. Изменение архитектуры описано спецификацией до написания кода.

**Макетов и дизайн-системы нет.** Оформление — две таблицы стилей
`static/css/theme.css` и `app.css`. Проектирование интерфейса как отдельного направления
работы не ведётся.

## §7. Если сломалось

### Шаг 0. Определить, сломался бэкенд или прокси

Это первое, что нужно сделать, и самая частая потеря времени: стандартная страница
`Welcome to nginx!` выглядит как «сервис не заработал», хотя контейнер полностью исправен.

```bash
# 1. жив ли контейнер
cd /opt/ipsas
docker compose ps

# 2. отвечает ли приложение напрямую, минуя nginx
curl -s http://127.0.0.1:8000/health

# 3. что отдаёт прокси
curl -I http://127.0.0.1/
```

| Симптом | Диагноз | Что делать |
|---------|---------|------------|
| `Welcome to nginx!` | активен стандартный сайт | удалить `/etc/nginx/sites-enabled/default`, проверить симлинк `ipsas.conf`, `sudo nginx -t && sudo systemctl reload nginx` |
| `502 Bad Gateway` | прокси работает, бэкенд не отвечает | `docker compose ps`, затем `docker compose logs --tail=50` |
| `502` сразу после `up -d` | контейнер ещё не успел подняться | `sleep 10` и повторить; на старте нужны секунды |
| `504 Gateway Time-out` | бэкенд отвечает слишком долго | вероятна зависшая фоновая задача или загрузка большого файла |
| контейнер `running`, но `/health` не отвечает | процесс поднялся, но не инициализирован | `docker compose logs` — искать ошибки чтения `SECRET_KEY` или XSD |
| контейнер перезапускается по кругу | падение при старте | `docker compose ps` покажет `restart`; читать логи |

### Шаг 1. Найти ошибку

```bash
docker compose logs --tail=100 ipsas
```

Каждый ответ с ошибкой содержит `request_id`. Искать в логах по нему:

```
request_id=3f7a91c2b0e4 ipsas_error=…
request_id=3f7a91c2b0e4 unexpected_error=…
```

Стек-трейс наружу не отдаётся намеренно: пользователь получает только `request_id`. Это
осознанное поведение, а не повреждение.

### Шаг 2. Типовые сбои

**Формы отвечают ошибкой CSRF.** Значение `SESSION_COOKIE_SECURE` не соответствует схеме
доставки. В текущем развёртывании `docker-compose.yml` задаёт `false` принудительно, поэтому
форма работает; поломка возможна только при запуске в обход compose.

**Сервис «перегружен», хотя нагрузка обычная.** Не выставлен `TRUST_PROXY_HEADERS=true`: за
nginx все запросы приходят с адреса прокси и делят один лимит 30 запросов в минуту. В
текущем развёртывании compose задаёт `true` принудительно.

**Сервис работает на старой версии кода.** Забыт `--build` в `docker compose up`.

**Не перезапускается после `git pull`.** Проверить, что `.env` на месте и не пуст: Compose
падает на старте при пустых `SECRET_KEY` или `ISSUE_FETCH_ALLOWED_HOSTS`. В production без
`SECRET_KEY` приложение не стартует — это единственная настройка, способная дать именно
такой симптом.

**Не удаётся подключиться к Docker.** Не запущен daemon: `sudo systemctl start docker`.

**`cannot connect to the Docker daemon` после правки прав.** Требуется перелогиниться в
сессию, чтобы обновилась группа `docker`.

**Изменилось окружение, но поведение прежнее.** Переменные читаются при создании контейнера;
`docker compose up -d` без `--force-recreate` может не пересоздать контейнер. Проверить
фактическое значение: `docker compose exec ipsas printenv PLATFORM_APPLY_ENABLED`.

**Песочница не отвечает.** Хост `f23g45.rcsi.science` не в `ISSUE_FETCH_ALLOWED_HOSTS` —
SSRF-фильтр блокирует запрос. Проверить значение переменной.

**Запись в ОПУС не отправляется.** Проверить `PLATFORM_APPLY_ENABLED`: при `0` форма
готовит payload и останавливается, не отправляя POST.

**Потеряны незавершённые разборы выпусков.** Не подлежит восстановлению: состояние в памяти
и во временных файлах. Запустить заново.

**Учётные данные платформы отклонены.** Логин или пароль неверны либо у учётной записи нет
прав на запись. Проверяется в логах ошибкой авторизации Платформы.

### Шаг 3. Откат

```bash
cd /opt/ipsas
docker compose logs --tail=100 > /tmp/ipsas-before-rollback.log
git checkout <рабочий-коммит>
docker compose up -d --build
bash deploy/smoke-test.sh http://127.0.0.1/
```
